### UR-001 — 前端不是换皮，而是按 OS 逻辑从头重做

- **状态 / 优先级：** `current / P0`
- **真实需求：** PAWOS 所有现有页面、侧边栏功能、框架、布局、消息流和
  结果展示都必须从用户任务出发重新设计。旧前端可以作为功能清单和回退，
  不能作为新界面的结构模板；改颜色、换壁纸、套壳或嵌入旧页面都不算完成。
- **必须保留：** 原有每项可用能力、数据入口、操作路径和结果类型；“重写”
  指展示与交互重写，不是功能删减。
- **禁止：** 在核心功能未可用前用壁纸、美术或无关测试代替界面工作；把
  “优化 UI”缩减成色板调整；把 Agent 的思维、愿景或内部运行结论写成产品
  文案。
- **用户可见验收：** 每个 App 都有符合其任务的独立信息架构和操作路径，
  用户看到的是能工作的 OS App，而不是控制台网页或旧页嵌套。
- **原话依据：** “每一个侧边栏的功能都得重新推倒设计”“每个页面前端都
  得大改”“前端我说了从头写”“说了彻底重新写，我原来的功能你得保留”。
  来源：当前任务；旧任务 turns `<redacted-related-turns>`。

### UR-002 — Agent 只有一个入口，Session 与 Room 在入口内选择

- **状态 / 优先级：** `current / P0`
- **真实需求：** 顶层只保留一个 **Agent** 工作入口。新建或进入工作时，
  通过明确选择区分普通 `Session` 与多人 `Room`；两者仍是不同 Runtime
  对象、数据和工作流，但不再暴露为两个割裂的顶层入口。
- **必须保留：** Session 列表、Room 列表、恢复历史、角色/参与者、分别独立
  开窗以及各自完整工作区。共享入口不等于合并 Runtime 所有权。
- **修正关系：** 本条 `supersedes` 旧任务中“Agent 与 Rooms 分别作为顶层
  App”的导航方案，只修正入口和信息架构，不撤销 Room 的多人协作能力或
  Session/Room 的独立身份。
- **用户可见验收：** 用户只需进入 Agent 一处；在新工作选择器中选 Session
  或 Room，之后进入对应的完整工作区，历史项目也能按类型检索和恢复。
- **原话依据：** “agent入口改这样子，本来就应该一个入口，通过选择来区分
  room和session。……原来的新建不太好”。来源：当前任务。被修正旧原话：
  “Agent 对话、Session 列表、角色”“Rooms 多人协作、Room 列表、工作流图”。

### UR-003 — Session 必须恢复原有完整能力，并重新设计消息与结果渲染

- **状态 / 优先级：** `current / P0`
- **真实需求：** Session 不能只是聊天框或静态样例。必须从用户视角重新组织
  完整会话：发现/搜索/新建/恢复、项目与工作区、角色与模型、权限、附件、
  输入与发送、流式消息、思考摘要、工具调用、任务/计划、结构化结果、代码/
  表格/媒体等结果渲染、错误/重连/取消/继续、用量和子 Agent 运行结果。
- **必须保留：** 旧 Session 已有功能与“各种结果渲染”；可借鉴 Tutti 或
  现成 Agent 前端的交互和渲染，但必须适配 PAW 的 Pi Session 数据、权限和
  工具循环，不能引入第二套 Runtime。
- **禁止：** 只有空白聊天页、只有最终文本、隐藏工具/任务结果、删掉原功能，
  或仅凭静态页面声称可用。
- **用户可见验收：** 用真实历史 Session 和真实运行覆盖输入、流式过程、
  工具/任务、不同结果卡片、恢复/重连和最终答复；信息稳定、不跳动、不丢失。
- **原话依据：** “消息流的前端也得改”“Session 与 Room……至少要像之前
  一样功能齐全”“我原来session那么多功能，还有各种结果渲染”“你大不了
  抄现成的agent前端”。来源：当前任务。

### UR-004 — Room 是完整可执行的多人协作工作区

- **状态 / 优先级：** `current / P0`
- **真实需求：** Room 必须能创建、恢复和实际执行多人工作，展示参与者、
  平等的直接 `@`/通信、真实 WorkItems、任务 Workflow 图、按时间排列的消息
  与每次 loop 卡片、分工/执行状态、伙伴交付、审批和最终答复。主 Room 窗口
  完整存在，每位 Partner 可按桌面场景打开卫星小窗。
- **必须保留：** Room 与普通 Session 的身份和治理差异；审批若存在必须在
  Room 内；伙伴结果和最终整合不能被内部诊断文案替代。
- **禁止：** 空“审阅”页；没有分工却展示协作完成；把父 Agent 当唯一转发
  中心；`workItems=0` 时伪造流程图；只显示“本轮已结束/无结构化回执”而不
  显示用户要的最终结果。
- **用户可见验收：** 一个真实 Room 生成非零 WorkItems，图能表达任务依赖
  与参与者关系，消息按时间稳定渲染，每次 loop 单独成卡，主窗与卫星窗都可
  操作，最终答复可见且能追溯伙伴交付。
- **原话依据：** 旧任务中“每个patent可以成为一个小窗口”“审批……要在
  room里面”“消息按时间顺序，我没看到最终答复”“一次loop一个框”“确保
  你们每个人是平等的”“图……是一个任务的workflow图”等原话。

### UR-005 — Tutti 是迁移与优化基线，不是产品内核

- **状态 / 优先级：** `current / P0`
- **真实需求：** 直接吸收或迁移 Tutti 已成熟的窗口、Session/Room、Files、
  Browser、Terminal、流式渲染和交互机制，并在 PAWOS 中做得更流畅、更易
  拆卸、更适合多窗口和安装卸载。旧前端保留为切换/回退，直到迁移验收。
- **必须保留：** Pi 是唯一 Agent Runtime；Tutti 是实现与体验参考。迁移代码
  必须落在 `7155/personal-agent-workbench`，不修改上游参考仓库。
- **禁止：** 只“借鉴风格”却重造更差的交互；复制 Tutti 的产品身份、运行时
  所有权或历史包袱；以截图或 mock 代替迁移后的真实功能。
- **用户可见验收：** 拖动、开窗、滚动、流式消息和结果展开不抽搐、不跳动，
  体感至少不低于参考前端；旧前端能明确回退。
- **原话依据：** “不止是吸收，就是把他实现迁移做到更好”“他加载都比我们
  快”“拖动卡顿”“在tutti上面优化，使得更加可拆卸，动效更适配”。来源：
  旧任务相关 turns。

### UR-006 — PAWOS 必须呈现真正的桌面 OS 交互

- **状态 / 优先级：** `current / P1`
- **真实需求：** 参考 ChromeOS/ChromeOS Flex 和用户提供的 HTML，把 PAWOS
  做成浏览器承载的桌面操作系统：桌面/项目场、窗口、Dock/Launcher、搜索、
  多窗口、原生式右键菜单、框选、焦点、拖拽、最小化/恢复、层级和快捷操作。
  右键与框选必须由 PAWOS 接管为系统交互，不能弹网页默认菜单。
- **视觉要求：** 保持三套主题并继续优化，色彩和层次至少对齐用户参考 HTML；
  漂亮、酷炫但首先服务操作，不靠无意义装饰。
- **用户可见验收：** 用户第一眼能识别为 OS；鼠标、键盘、右键、框选、窗口
  和多任务行为一致，交互状态可预测且可中断。
- **原话依据：** “可以参考一下chomeos”“chromeos-flex的动效”“在系统
  里面，右键和框选这些就不是网页的那些弹出了”“最起码是os”“我的面板
  是os交互要优于tutti”。来源：当前任务及旧任务。

### UR-007 — 动效是全局交互系统，不是最后补几个特效

- **状态 / 优先级：** `current / P1`
- **真实需求：** 每个 App 和系统层都要设计有目的的转场与微交互，覆盖开窗/
  关窗、选择、切换、展开、加载、流式更新、拖拽、Dock/Launcher、菜单和
  错误恢复。动效应参考 ChromeOS Flex 的物理感，稳定、连贯、可打断，并
  遵守 reduced-motion。
- **禁止：** 页面跳动、布局抖动、流式内容导致反复重排、过度弹跳或纯装饰
  动画掩盖加载问题。
- **用户可见验收：** 核心动作有一致反馈，拖动与流式渲染稳定；动效关闭或
  降级后仍可完整操作。
- **原话依据：** “每个页面都得改特效交互动画”“动效还得疯狂优化”“网页
  一直跳动抽搐”。来源：当前任务及旧任务。

### UR-008 — Browser 是 PAW 内置、隔离且由 Agent 直接控制的系统 App

- **状态 / 优先级：** `current / P0`
- **真实需求：** Browser 直接作为 PAWOS App 提供，天然与 Agent 打通，
  Browser 自身就是隔离执行环境。Agent 能控制标签页、导航、读取页面、点击、
  输入、下载和其他浏览器能力；人和 Agent 共享同一可见状态。
- **禁止：** 浏览器扩展、插件 side panel、browser-copilot 或额外中间层成为
  主路径；把“控制权”做成只读演示。
- **安全边界：** “全权控制”表示在 PAW Browser 沙箱与用户授权边界内完整
  控制，不表示绕过系统权限、站点权限或用户确认。
- **用户可见验收：** 不安装插件即可由 Agent 完成真实浏览任务，用户能看见
  并接手相同标签页；失败、权限和下载状态清楚可见。
- **原话依据：** “paw内置的”“ai全权控制的浏览器”“不用插件这些”“不用
  中间层了”“终端就是系统终端，浏览器也是”。来源：当前任务及旧任务。

### UR-009 — 所有原侧边栏能力要重组为 OS App，不得遗漏

- **状态 / 优先级：** `current / P1`
- **真实需求：** Project Field/Wayfinder 是首页与项目选择，不是普通 App；
  顶层 App 包括 Project Workbench、Agent（内选 Session/Room）、Memory、
  Knowledge、Input Studio、App Center、System Monitor、System Settings、
  Files、Browser、Terminal。每个功能逐一对齐旧能力后重新设计。
- **功能含义：** Project Workbench 管概览/任务/WorkDocuments；Memory 与
  Knowledge 保持不同治理；Input Studio 包含语音、输入法/词库/输入记录且
  输入法控制本身是 App；App Center 把 Pi Package/插件作为可安装应用；
  Monitor 管上下文、运行记录、排障；Settings 管配置、安全、治理、模型与
  Provider；Files 迁移优化 Tutti；Terminal 使用系统终端语义。
- **禁止：** 因重写界面而删掉任一旧侧边栏能力，或用一个通用 dashboard
  把所有 App 变成同构卡片。
- **用户可见验收：** App 清单逐项完成能力对照和真实操作验收；项目/文档、
  Session/Room 等对象可按需求独立开窗。
- **原话依据：** 旧任务中的完整 PAWOS 顶层清单、“每一个功能都得重新设计
  ui和前端”“先完整主干，就是我们哪些侧边栏的功能作为app”。

### UR-010 — 文档先对齐，Agent 按 WorkDocument/WorkItem 找上下文并回写

- **状态 / 优先级：** `current / P0`
- **真实需求：** 需求变化先落到项目文档，再规划和开发；所有负责 Agent 必须
  能从 WorkItem/WorkDocument 引用找到自己负责部分、相关 Session 和活动
  文档，完成后写回进度、结果与证据。采用软约定和现有引用链，不再造第二套
  上下文系统。
- **文档规则：** 用户原话不能只被摘抄；顶部先形成完整、无损、可追溯的真实
  需求账本，原话证据随后保留。每条来源必须映射到需求或明确标记非需求/
  重复/仅参考，修正不能覆盖旧证据。工作完成、部分完成或阻塞时也必须回写
  结果、变更、验证证据、未验证边界、残余风险和文档 revision receipt。
- **软约束：** WorkDocument 用于定位上下文、回收和交接，不是所有任务的硬验收门。
  登记、hash 或 authority 回写失败时只记录一次 `documentSync=pending/failed`、Trace
  和可见提醒；已通过真实功能验收的 WorkItem 仍可收口，不因文档失败自动
  return/retry。只有交付物本身就是文档时，该文档失败才影响 requirement verdict。
- **禁止：** Agent 各自开工却不写文档；完成后不标注；handoff 只写实现摘要
  而漏掉原始需求；把 Runtime 状态从 Markdown 猜出来。
- **用户可见验收：** 新 Agent 仅凭分配引用即可定位需求、上下文、当前工作和
  回写位置；需求文档能从原话追到规范，也能从规范反查原话。
- **原话依据：** “技能流应该是先对齐需求呀”“各自干活并没有先在文档上写”
  “就是文档缺少同步”“我的需求全部记录文档”“我的原话得放最上面”“整理
  为完整无损信息”“这些话对应的真实需求是什么，得整理出来”“最后完成了，
  也得记录”“前面需求一个都不能少”“写handoff，所有需求”“你记录需求到
  文档”“文档不过就不过，他们因为文档重复了半天了”“硬限制软一些”。
  来源：当前任务及旧任务。

### UR-011 — 用户界面只显示用户需要的信息

- **状态 / 优先级：** `current / P1`
- **真实需求：** 界面文案围绕对象、状态、下一步和结果；内部推理、愿景口号、
  设计比喻、实现诊断和无行动价值的欢迎语不得进入产品界面。
- **禁止示例：** “飞轮的起点”“继续最近的会话……或打开一个 App……”“本轮
  只结束了伙伴的 Pi 回合……”等 Agent/实现视角文案。
- **用户可见验收：** 每段常驻文案都能回答“我在哪里、发生了什么、我能做
  什么”；删除后不影响任务的信息不应占据主界面。
- **原话依据：** “你不能把你的思维写进前端”“只保留用户必要的信息”“不
  显示这个”。来源：旧任务。

### UR-012 — 美术资源最后做，使用 GPT Image 2，但不安装 `openai` 包

- **状态 / 优先级：** `current / P2`
- **真实需求：** 在信息架构、功能、布局、交互和动效完成后，最后用 Codex
  已有的 GPT Image 2 生图能力生成缺失美术，或输出提示词让用户生成。最终
  美术质量至少赶上 ChromeOS，并适配三套主题和实际组件尺寸。
- **禁止：** 为生图给项目安装 `openai` Python 包；把壁纸当作前端完成度；
  在核心 UX 未完成时优先消耗时间生成装饰资源。
- **用户可见验收：** 资源有明确用途、尺寸、主题变体和资产归属；去掉资源后
  功能仍完整，加入后整体品质达到产品目标。
- **原话依据：** “最后一步要用GPTimage2生成对应的美术资源”“你codex啊，
  为什么装 `openai` 包”“缺少的美术资源你可以发提示词给我，我去生图”“你
  弄壁纸一点用都没有”。来源：当前任务及旧任务。

### UR-013 — 安装、自举、卸载、回退和真实浏览器验收属于交付

- **状态 / 优先级：** `current / P0`
- **真实需求：** 最终交付是项目自己的 Pi `0.84` Runtime 加适配完成的 PAWOS
  前端，能按项目技能流安装、自举、升级/卸载并回退旧前端；安装后在真实
  Browser 中完成 Session 和 Room 端到端测试。
- **禁止：** 把单测、构建、静态截图或 mock 当作安装后的可用性证明；修改
  Tutti 上游来完成 PAW 安装。
- **用户可见验收：** 从干净入口完成安装与启动，真实创建/恢复一个 Session
  和一个 Room，覆盖关键消息与结果渲染，验证卸载/回退；证据区分源码、构建、
  安装、Runtime 健康和前台验收。
- **原话依据：** “注意自举和安装卸载”“旧的前端先留着，后续可以切换”
  “最后是0.84的我们才改好的pi加上适配好的前端，安装好后能够浏览器测试
  session和room通过”。来源：旧任务。

### UR-014 — Subagent 必须批量并发作为后台工具，父 Agent 同步推进不被阻塞

- **状态 / 优先级：** `current / P0`
- **真实需求：** 在 Session 内使用 subagent 时，必须一次性批量发起多个子 Agent（并发执行不同维度的调研、检查或独立子任务），并将它们作为后台异步工具运行；父 Agent 同时继续推进自身工作，在一般情况下不得被 subagent 阻塞或空转等待，待 subagent 事件返回时再响应式消费与整合。
- **必须保留：** 任务边界明确的 TaskBrief、独立的模型/人设/权限配置、子 Agent 结果作为证据而非自动决策、父 Agent 统一集成与负责。
- **禁止：** 串行单发子 Agent；发起子 Agent 后父 Agent 停滞/阻塞/忙轮询等待；将私有子 Agent 混淆为 Room Partner。
- **用户可见验收：** 委托多路任务时能够批量并发发起后台 subagent，父 Session 不中断自己的工作流，待子任务完成事件返回后自动聚合分析。
- **原话依据：** “修改这个项目的subagent。subagent你要用就一次用多个。而且是作为后台工具，等他们事件返回，你是同时做你的工作，一般情况不要被subagent阻塞”。来源：当前任务。

### UR-015 — 与 Tutti 对应的功能直接迁移，PAW Runtime 与 Room 语义留在 PAW

- **状态 / 优先级：** `current / P0`

### UR-023 — Room 用真实 FlowPacket 投影网状协作与文档/Plan 扇出

  的特效。点击活动包、边或时间线条目可查看摘要和上下文/文档；持久关系线保持
  克制，活跃包优先，避免长期“意大利面”。reduced-motion 下使用即时边高亮和
  有序流转日志。
- **真实性：** 只投影 Room dispatch、peer message、公开 ask/reply、WorkItem、
  ContextRef 和 WorkDocument receipt 等权威事件，不显示私有 reasoning，不推测
  未发生的分发，也不把动画完成当 Runtime 送达证明。
- **用户可见验收：** 能从主需求沿边追到负责人，再追踪问题返回、用户答复、plan/
  文档生成与多伙伴扇出；任一伙伴互发也能在网状窗口和时间线中找到同一个真实
  事件及其上下文。
- **原话依据：** “主窗口发一个需求……只发给一个负责的 agent”“一个消息就是

- **生命周期：** 正常关闭 Browser、停止控制、重启 PAW 或更新 Runtime 不删除
  Profile。只有用户明确执行 Chromium 自己的清除浏览数据或 PAW 的显式 Profile
  重置动作时才清除。
- **用户可见验收：** Browser 工具栏能打开该受管 Chromium 的原生 History；关闭
  并重新启动 PAW Browser 后，先前记录和仍有效的登录态继续存在。现有 Agent
  command trace 只是运行活动，不作为另一份用户浏览历史呈现。
- **原话依据：** “这个独立的浏览器，它能保留历史吗？我希望能够。保留历史”；
  最新修正：“不分层……当前是先跑通，不要防御性设计编程”。来源：当前任务。

### UR-025 — 所有 App 保持干净，不把设计与实现思路写进界面

- **状态 / 优先级：** `current / P0`
- **真实需求：** 每个 PAWOS App 只显示该 App 的内容、状态和完成当前操作真正
  需要的控件。不得把产品设计思路、架构说明、权限宣言、实现协议、迁移语言、
  沙箱说明或自我解释写成可见 UI；不得用多余徽章、状态条、说明卡和装饰面板
  填满空白。
- **Browser 修正：** Browser 是干净浏览器，只保留标签页、标准导航、地址栏、
  必要菜单和网页内容。空白页必须保持纯空白；不显示“Agent 完整控制权”“CDP
  直连”“独立受管 Profile”“交互网页/CDP 视图”等实现说明，也不因空白页没有
  snapshot 显示技术错误。
- **执行方式：** 先直接迁移成熟参考项目的对应功能与交互，再做必要的 PAW 适配
  和简化；当前阶段不做防御性扩层或过度设计。
- **原话依据：** “我讨厌这些过度设计，还有你把你的思路写在上面”“完全就浏览器

  写上去。不要过度设计，不要防御性编程”。来源：当前任务及所附截图。

### UR-027 — 取消“澄”和角色设定，Agent 对齐 Tutti 的模型与快捷提示词

- **状态 / 优先级：** `current / P0`
- **命名修正：** 产品界面、native 窗口标题和应用菜单不再使用“澄”。使用 PAW /

  角色库、角色编辑或角色选择入口。Agent Composer 直接对应 Tutti 的设置形态：

  底部；快捷提示词可新增、编辑、删除并插入输入框，不另造 PAW 专属设置页或角色层。
- **兼容边界：** 旧 Runtime 数据中的 `roleId`/`roleVersion` 在迁移期间可作为内部

### UR-028 — Session/Room 主管 Agent 对每项工作负责到底，执行与验证形成闭环

- **状态 / 优先级：** `current / P0`
- **闭环合同：** 一项实质工作必须按“用户原始需求与修正 → 当前精确需求与验收 →
  可执行 WorkItem → 执行 → verifying → `complete` / `partial` / `blocked` 收尾回执”推进。
  Skill 是各阶段按需调用的方法，不是第二套 Runtime，也不能代替主管 Agent 的责任。
- **Session 责任：** Session 主 Agent 是整项工作的主管与最终集成者。它持续识别未完成、
  未闭环、失去 owner、失败或只完成一部分的 WorkItem，并负责分配、重分配、退回正确阶段、
  集成证据和给出一个真实终态。执行 Agent 可以有多个；验证 Agent 也可以按风险拆成多个。
- **Room 责任：** Room Facilitator 主管 Room 的总体闭环；每个 Partner 对被分配的具体
  WorkItem 负责。每项工作必须可看到 `requirementRefs`、当前执行 owner、最终 accountable
  owner、Session/对话引用、WorkDocument、当前状态、下一步、验证责任与证据。
- **并发 subagent：** Session 可以不调用 subagent；一旦决定调用，应把多个独立工作面
  一次性批量并发交给多个后台 subagent，父 Agent 同时继续自己的工作，并在事件返回时
  响应式整合。只有一个连贯工作面时留在父 Agent 本地，不把串行单发/等待包装成并发优势。
- **上下文模式：** 每个 delegated task 使用 `fresh/new` 还是 `fork`，由主管 Agent 根据
  该任务需要的连续性、隔离程度和上下文复用决定。两种模式都必须作为受支持的一等选择；
  Skill 不得硬编码某个模式天然更好，也不得因为偏见拒绝另一个模式。无论选择哪种模式，
  都要有边界清晰的 TaskBrief、引用、能力与验收合同。
- **双重 verifying：** 分开检查并记录两个问题：一是实现/命令/真实路径能否跑通；二是
  结果是否解决了当前精确需求。只通过一个轴不能宣称闭环；失败必须回到负责修复的阶段和
  owner，而不是停在一个孤立的 review 结论。
- **用户可见验收：** 一次真实 Session/Room 工作能显示多个执行责任、必要时的一批后台
  subagent、父 Agent 的同步推进、两个验证轴、未闭环项的重分配/回退，以及每项工作的
  complete/partial/blocked 结果和文档/证据回执。Markdown 状态只能作为语义记录，不能伪造
  Runtime 的 running、owner 或 terminal 状态。
- **原话依据：** “verifying这个就是检查两个方面，一个就是 也许是否能够跑通，另一个
  就是是否把需求给解决了，对吧？”“闭环”“Session 主 Agent……执行 Agent这个也是不止
  一个执行，是多个执行……验证 Agent”“如果调用的话，咱们一次性可能就调用多个，因为
  这个……一方面就是为了加快速度，另一方面就是节省上下文”“隔离上下文是否可以上上门
  是由具体家政决定，因为两个都是，一个是4个，一个是NEW。他们都支持，你不要在智能里面，
  觉得不一定好。接下来就把这些技能闭环吧。”来源：当前任务。

### UR-029 — 每个 App 按对应成熟功能重做，不保留假操作和宣传型入口

### UR-030 — Agent 设置是独立真实功能，不与 Composer 混为一页

- **真实性：** 设置页中的值必须被新建 Session 与快捷提示词选择器实际消费；
