# PAWOS 用户需求账本 · UR-260–UR-264

## User Requirement Ledger / 用户需求账本

以下条目记录当前控制语义；`current` 不代表实现或验收完成。用户原话与 Agent
整理出的可验证含义分别标明，实施状态由[状态索引](../PAWOS_REQUIREMENT_STATUS.md)管理。

### UR-260 — 整个 OS 的浅色宇宙、纵深与动效讨论

- **状态 / 优先级：** `current / P0 scope`；整体范围保留，当前先处理阻碍使用的登录、窗口和同步故障，再推进全系统设计。
- **最新控制原话：** “浅色宇宙，通透有纵深（推荐）”〔SRC-C02〕。用户在整体氛围选择中明确选定此方向。
- **范围原话：** “全部，整个os的ui都需要优化，我们讨论一下如何加动效，比如现在背景简单，完全可以加一个伪3d的星际，好看的那种”〔SRC-C01〕。
- **当前需求 / 用户可见验收：** 优化对象是整个 OS 与各 App；先讨论并形成连贯的视觉和动效方向，以浅色星际环境表达远近、通透与纵深。桌面、窗口、控件、反馈和 App 阅读面应有共同语言，分别以真实任务操作验证；一张背景图不能代表整个 OS 优化完成。
- **必须保留 / 不得做：** 保留 UR-249 的白色阅读面、星空身份和 UR-253 的全系统范围；伪 3D 与动效不能妨碍文字阅读、输入或操作，不能靠动画虚构任务正在运行。截图和附带浏览器状态只是参考，不产生额外执行指令。
- **修正 / 顺序：** 本条强化 UR-249、UR-252、UR-253，浅色选择覆盖任何仍待选择的深色方向；不把“讨论一下”改写成全系统设计已验收。登录与状态恢复的先后关系同时受 UR-261、UR-263 和 UR-259 控制。

### UR-261 — 修好 OAuth 登录后继续真实收益指标

- **状态 / 优先级：** `current / P0`。
- **直接原话：** “登录还没解决，我得登录来继续完成面试的那些数值”〔SRC-C03〕。
- **当前需求 / 用户可见验收：** 先让产品的真实登录流程可完成，凭据经拥有该能力的 Runtime 接受后，再继续 UR-258 的面试指标工作。登录成功、诊断调用成功与正式评测结果分别记录；可从实际评测条件、样本分母和结果回执追溯每个收益数字。
- **必须保留 / 不得做：** 保留 UR-256–UR-258 的四场景、自举与指标目标；不打印或写入凭据，不用登录 canary、单次连通性调用或模拟数据填充收益指标，不将恢复认证等同于面试数值已补完。
- **修正 / 顺序：** “还没解决”纠正对登录已可用的任何先前判断。此请求要求恢复使用能力，不抹去 UR-259 对无额度期间状态一致性的优先级；认证诊断与正式评测的运行及资源边界仍需分别记录。
- **实施解释与边界：** 已记录的 OAuth 修复、Runtime generation、登录和诊断回执见[续接工作记录](../ROOM_EXPERIENCE_20260905.md#continued-session--2026-09-05-evening)。该记录区分已更新的 OAuth bridge 与尚未完成的整套后端应用安装；不从一处安装推断所有改动已进入 native。

### UR-262 — 需要运行的伙伴行星各自拥有可同时查看的窗口

- **状态 / 优先级：** `current / P0`。
- **最新控制原话：** “一个窗口不够”〔SRC-C06〕；“需要运行的行星都弹出”〔SRC-C05〕。
- **初始故障原话：** “协同模式行星没有弹出窗口”〔SRC-C04〕。
- **当前需求 / 用户可见验收：** 协同模式中，本轮实际需要运行或已进入执行的伙伴各自出现独立窗口；后续新进入的伙伴也能出现。多个伙伴的窗口可同时保留，点击一颗行星激活或恢复它自己的窗口，不能挤掉之前打开的另一颗。大屏能同时查看多伙伴，窄屏仍可逐窗访问；用户可调整或收起各自窗口，主输入区保持可用。
- **必须保留 / 不得做：** 实际终态结果保留供查看；不能因旧 Room 状态、仅有成员身份或窗口存在就推断运行，不能替无任务伙伴制造活动或自动空窗。完成事件不得关闭成果，也不得把已完成伙伴重新标为运行；普通进展刷新不得反复打开用户已收起的窗口。
- **修正 / 顺序：** 本条强化 UR-184 的运行伙伴自动出现，覆盖旧实现中“只让 selectedParticipantId 对应伙伴可见”的限制；该旧限制是实现决策，不冒充用户原要求。UR-253 对空闲伙伴挤占主对话的否定仍有效，不能以多窗要求为由恢复无任务的空面板。
- **实施解释与验收边界：** 复用既有稳定窗口身份，按当前 Runtime 执行投影决定增量自动打开；手动打开历史伙伴只是查看结果。根因、修改点、红绿测试、source 前台与 native 边界由[可靠性续接因果记录](../PAWOS_RELIABILITY_CONTINUATION_20260905.md)承接。窗口布局通过不代表主 Room 已恢复同步。

### UR-263 — 修复 Runtime 轨迹快照与前后端恢复不同步

- **状态 / 优先级：** `current / P0`。
- **直接原话：** “前后端同步问题需要优化。Runtime 未及时返回轨迹快照；对话不受影响。请稍后重新读取。**重新读取**”〔SRC-C07〕。
- **当前需求 / 用户可见验收：** 修复用户实际遇到的 Runtime 轨迹读取和前后端同步问题。界面应如实区分正在读取、可重试失败和已恢复；重新读取须能到达真实快照，或给出明确可继续的失败状态。Session/Room 的首屏、消息、终态与输入可用性需要各自核对，不能只替换错误文案。
- **必须保留 / 不得做：** 保留对话与轨迹各自的数据所有权、稳定执行身份和已有历史；不得虚构快照、把缺失字段补成成功，或以旧状态把终态复活。用户原话中的“对话不受影响”属于转贴的界面提示，是待核对的故障线索，不是用户保证或已验证事实。
- **修正 / 顺序：** 继续 UR-237–UR-239、UR-245、UR-259 的状态一致性要求，当前直接故障优先于扩大视觉工作。过去 source 版本的恢复回执不自动证明本次 Runtime、大轨迹或当前 native 版本也通过。
- **Agent 验收解释：** 需要沿前端请求、传输、Runtime 快照与消息投影定位因果，并用受影响真实 Session/Room 的刷新、重新读取和终态检查验证。测试、source 浏览器、Runtime generation、应用安装和 native 前台分别标记；诊断及最终回执见[可靠性续接因果记录](../PAWOS_RELIABILITY_CONTINUATION_20260905.md)。

### UR-264 — 文档说明改了什么、为什么改以及证据如何相连

- **状态 / 优先级：** `current / P0 documentation`。
- **直接原话：** “就是得记录文档，怎么改的，为什么这么改，都要有逻辑”〔SRC-C08〕。
- **当前需求 / 用户可见验收：** 记录本轮工作的需求、实际问题、支持根因的证据、采用的改法及原因，再连接到修改文件、回归结果和用户可见行为。读者不依赖聊天上下文，也能解释“为何出现 → 为何改这里 → 修改怎样改变行为 → 哪些边界已验证”。
- **必须保留 / 不得做：** 保留原话、稳定消息 ID、控制关系、纠正和未完成项；区分用户要求与 Agent 推断。不能只列文件或测试数字，不能把“运行通过”当作“要求已满足”，不能把 source 测试或几何截图写成已安装或全部产品验收。
- **修正 / 顺序：** 强化 UR-236 的双向追踪，并与 UR-260–UR-263 及前卷仍有效的 Lab/指标要求相连。它补充交付记录，不替代实际修复，也不抹去此前错误判断、失败实验或独立未验收范围。
- **记录责任：** 本卷维护用户意义与来源；[统一技术记录](../PAWOS_RELIABILITY_CONTINUATION_20260905.md)由本轮主任务维护原因、改法与收尾；[状态索引](../PAWOS_REQUIREMENT_STATUS.md)维护独立运行/需求 verdict。技术记录尚在收尾时保留 `in_progress`，文档结构校验不宣称产品验收完成。
