## User Requirement Ledger

### UR-225 — Trace 报告采用倒金字塔与扫读/深读双层结构

- **状态 / 优先级：** `current / P0 Trace report comprehension`
- **首要目标：** 不了解 PAW/Pi 的读者在 10 秒内知道：发生了什么、为什么、有多确定、
  现在能做什么。不能先穿过空章节、未知矩阵或内部协议名才看到真正结论。
- **第一屏 TL;DR：** 一句可独立成立的白话结论、真实状态徽章和三个能解释判断的关键
  数字。本次示例是持续时间、冻结事件数、阶段回执数；数字必须由报告数据得出，不能
  为凑三项而伪造。判决、优先级和发现数量不能互相矛盾。
- **第二屏因果链：** 把嵌套错误拆成从任务到影响的图形链，每一环标记“已确认/待验证”。
  内部术语首现立即白话注释，例如 settlement（会话结算）、回执（阶段完成凭证）、冻结
  （不可变快照）。
- **第三屏已知 vs 未知：** 左侧仅列 2–3 条已确认事实；右侧把散落在全报告中的未知、
  未绑定、未冻结、无证据、未开始等集中成一个证据缺口清单。未知不能在十个章节重复。
- **第四屏发现：** 保留事实/假设/结论/候选修复/验证要求的证据结构，但标题用读者问题，
  例如“为什么失败？——会话结算超时（中置信）”。
- **第五屏行动：** 显式展示授权修复、沙盒重放/故障注入、新 Trace 对照验证三步，并让
  授权边界、执行动作和验证证据彼此分开。
- **折叠附录：** 时间线、环境快照、八维评分和 Evidence 目录默认折叠。正文只使用
  `[E1]`–`[E5]` 短别名，完整 60 字符证据 ID 仅在附录出现。全未知评分压成一行摘要，
  维度名只作为未来评估预告。
- **空态规则：** 需求矩阵、修复对照等无内容区域显示一行状态，不占独立大章节；缺失的
  时间线阶段用虚线占位，使“本应存在的回执缺失”本身成为可理解发现。
- **双层读者：** TL;DR、因果图、已知/未知和行动组成扫读层；附录、完整证据、环境与评分
  组成深读层，DOM/键盘顺序与视觉顺序一致。
- **验收：** 桌面与窄屏第一视口均先看到结论和行动方向；没有连续空章节、裸长错误串、
  正文长证据 ID 或全未知八行表；展开附录后仍可追溯全部原始证据。
- **来源原话摘录：**

  > 重写原则：倒金字塔 + 双层读者

  > 诊断报告只有一个目标：让读者 10 秒内知道发生了什么、为什么、有多确定、怎么办。

  > 结论先行：每份报告第一屏必须有一句能独立成立的结论

  > “未知”集中管理：一个缺口清单，不在各节重复

  > 双层读者：扫读层（TL;DR + 因果图 + 行动）和深读层（附录 + 证据）物理分开
