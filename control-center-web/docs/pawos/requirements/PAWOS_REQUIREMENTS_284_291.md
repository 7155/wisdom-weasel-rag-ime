# PAWOS 用户需求账本 · UR-284–UR-291

## 用户需求账本

后续 [UR-292–UR-297](PAWOS_REQUIREMENTS_292_297.md) 将这些优化要求纳入描述/路径输入、Agent 引导、可用 App 交付和完整前端重设计；本卷原话及优化证据边界保留。

本卷记录 Lab 的当前控制目标：针对真实垂直任务，比较模型、提示词、Skill、工具、工作流及 Harness，综合任务成功率与成本选择经过验证的合适方案。以下“解释 / 验收”是对原话的工程化整理，不是用户逐字指定的算法、阈值或已发生的效果。

> 上一份：[UR-278–UR-283](PAWOS_REQUIREMENTS_278_283.md) · [总索引](../PAWOS_REQUIREMENTS.md) · 下一份：[UR-292–UR-297](PAWOS_REQUIREMENTS_292_297.md)

### UR-284 — Lab 的核心成果是垂直 Agent 的成功率与成本优化

- **状态 / 优先级：** `current / P0`；延续 [UR-254–UR-255](PAWOS_REQUIREMENTS_254_255.md) 与 [UR-256](PAWOS_REQUIREMENTS_256_258.md)。P0 是依据用户明确的项目重点整理的优先级。
- **直接来源：** [LB-S06](#lb-s06)、[LB-S07](#lb-s07)、[LB-S08](#lb-s08)、[LB-S09](#lb-s09)。
- **控制语义：** Lab 要能针对垂直任务定位现有 Agent 的失败或成本问题，实际修改可优化对象，再运行对照、选择方案。故事主线是“Lab 如何优化一个垂直 Agent”，并解释为什么修改有效、在哪些条件下有效。
- **用户可见验收：** 从一个真实任务进入，能够看到原方案、失败或成本瓶颈、候选的实际改动、真实运行、前后成功率和成本、保留或拒绝的理由及对应证据。一次诊断完成或一次模型调用完成，都不能代替这条优化流程。
- **修正 / 保留：** 不能把主目标转成笼统证明 PAW/Harness 比网页聊天强，或把修复 PAW 自身缺陷自动定为唯一故事。已有安装、界面与可靠性工作继续按原需求维护；本条不取消它们，也不把它们当作垂直优化成果。

### UR-285 — 模型选择同时考量成功率与成本

- **状态 / 优先级：** `current / P0`；依赖 UR-284 的真实任务和成功标准。
- **直接来源：** [LB-S08](#lb-s08)、[LB-S09](#lb-s09)。
- **控制语义：** “合适模型”由任务成功率和模型执行成本共同决定。既比较模型本身，也比较模型配合工具、提示词、Skill 与工作流后的表现；较便宜模型能否达到任务要求需要实测。
- **用户可见验收：** 同一任务集、版本和判定口径下展示候选的成功分子/分母、失败类型、用量与成本来源，并说明质量与成本的取舍。优化搜索开销与选定方案的业务执行成本分别呈现；调用价格、单次成本和单位成功任务成本不混称。
- **解释边界：** “最优”指给定任务、约束和已测候选中的选择，不声称全局最优。质量门槛、预算、候选模型与样本量尚未由这轮原话确定；不得补造数值或把历史估算写成账单。没有同时提升两项，也应如实说明取舍。

### UR-286 — 工具按任务优化，验证结构化观测的收益

- **状态 / 优先级：** `current / P0`；候选必须在真实执行中装载生效。
- **直接来源：** [LB-S08](#lb-s08)。
- **控制语义：** 工具设计应服务具体任务。用户提出的改进方向是：相比大量读取原始内容，工具可整理出有用的结构化观测，减少上下文和噪音，让模型更容易完成任务。
- **用户可见验收：** 能查看原工具与候选工具的输入、输出和版本差异，比较实际读取量、上下文用量、工具调用、任务成功率与成本，并追溯到支撑结论的原始证据。
- **解释边界：** “结构化能减少噪音并提高表现”是待验证假设；不得预填收益或删掉不利观测来制造改善。工具不能偷偷加入参考答案。原话“用锐的工具”原样保留；按上下文理解为大量读取与结构化处理的比较，不据此虚构某个指定工具名称。

### UR-287 — 提示词、Skill、工作流与 Harness 固化有效的领域方法

- **状态 / 优先级：** `current / P0`；依赖具体场景的真实步骤与失败证据。
- **直接来源：** [LB-S07](#lb-s07)、[LB-S08](#lb-s08)。
- **控制语义：** 对可以总结成一个或几个流程的垂直任务，将有效方法写入提示词、Skill 或工作流，帮助模型按必要步骤取证和决策，减少偏离任务的探索；检验这是否能提高较便宜模型的成功率。
- **用户可见验收：** 展示失败发生在哪一步、修改了哪个规则或执行环节、候选实际加载了什么，以及修改后的逐任务结果。提示词、Skill、工具和工作流的改动分别留有可查看的版本差异；一次实验不要求全部修改。
- **解释边界：** 为识别改动原因，默认先做有明确假设的单因素对照，组合配置再作整体验证；这是工程化验收解释。原话“harmony harness”保留，当前按执行、上下文、工具调度和工作流支撑理解，不据此增加某种 Harmony 消息协议实现需求。

### UR-288 — RAG、企业知识库问答、运维排查共用优化方法，各有真实执行场景

- **状态 / 优先级：** `current / P0`；细化 UR-256，保留已有四场景工作，不擅自删去或新增业务承诺。
- **直接来源：** [LB-S09](#lb-s09)，结合 [LB-S07](#lb-s07)、[LB-S08](#lb-s08)。
- **控制语义：** 用户明确点名 RAG、企业知识库、企业问答及企业运维错误排查，这些场景都应能体现 Lab 选择成功率与成本合适方案的能力。知识库与问答是否拆成独立场景，由实际任务决定，不为凑数量重复计算。
- **用户可见验收：** 每个场景说明业务问题、原始数据、可用工具、执行环境、成功判定和可优化对象；共用“基线 → 定位问题 → 候选改动 → 对照 → 选择”的实验流程，但使用自己的运行器和判定器。
- **边界：** 不能只增加场景名称、说明和配色便称为支持，也不能全部强制为静态资料问答。此前选择云上诊断作为第一条调查线索仍可用于核查，但其是否适合主展示，要按真实优化空间和证据判断；没有规定这一条必须独占故事。

### UR-289 — 逐项说明任务环境、数据、工具与可执行范围

- **状态 / 优先级：** `current / P0`；这是选场景和解释优化结果的前置事实核查。
- **直接来源：** [LB-S02](#lb-s02)、[LB-S03](#lb-s03)、[LB-S04](#lb-s04)、[LB-S05](#lb-s05)。
- **控制语义：** 必须说明 Agent 到底做什么，获得哪些数据，数据是直接进入上下文、保存为文件还是按工具返回；它能读取、搜索、修改和运行什么，有没有源码、依赖、测试、沙箱或可访问的云端环境。
- **用户可见验收：** 读者能沿一条实际任务追踪“原始资料 → Agent 可访问的数据/工具 → 动作 → 产物 → 验证”。明确区分本机保存了资料与被测 Agent 实际能访问资料，也区分隔离的运行记录与真正提供写入、执行能力的沙箱。
- **修正 / 边界：** 代码修复场景要有实际可运行的复现、修改和测试/CI 证据；只读日志或冻结观测场景只能按实际诊断能力描述。不能因用户追问“它有沙箱吗”就记成所有场景必须配沙箱，也不能把快照重放写成已执行修复或已恢复云上服务。

### UR-290 — 先核实优化空间，并与合理的简单方案比较

- **状态 / 优先级：** `current / P0`；依赖 UR-289；用于 UR-284 的场景选择。
- **直接来源：** [LB-S05](#lb-s05)、[LB-S06](#lb-s06)、[LB-S07](#lb-s07)。
- **控制语义：** 用户质疑：如果把全部资料直接交给模型就能完成任务，只展示读取日志、找到上下文，不能说明 Lab 带来了什么优化。需要先识别真实失败、成本或执行瓶颈，再决定优化方向。
- **用户可见验收：** 适合完整上下文输入的任务，应比较这一合理简单方案与候选；记录可用信息、输入限制、成功率和总用量。如果简单方案已达质量要求，可以验证更低成本方案，但不能宣称不存在的成功率提升。
- **解释边界：** 用户的质疑是选题与验证要求，不是“所有模型一定能答对”的实验结论。不要靠隐藏任务本来可用的信息、故意劣化提示词或加入多余步骤制造优化必要性；工具数量和沙箱存在本身也不是收益指标。
