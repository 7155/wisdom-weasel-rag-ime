### UR-192 — 沙箱通过现有 Pi 插件市场提供，不另建市场

- **状态 / 优先级：** `current / P0 plugin/runtime integration`
- **真实需求：** 垂直 Agent 沙箱作为现有 Pi 插件市场中的插件提供和管理，沿用
  Pi Package 的发现、安装、启用与回滚路径；沙箱的 verify → TraceStore →
  EvalRun 测评链仍由系统真实 Runtime 承载并可被插件调用。
- **必须保留：** 插件市场是唯一发现和安装入口；插件能够配套 Trace Agent
  的排查技能，但不把沙箱再做成一套平行的市场、安装器或 Runtime。
- **禁止：** 不得为了展示另建第二个插件市场，也不得仅用静态 fixture、截图或
  文档宣称插件已安装、已启用或前台链路已通过。
- **用户可见验收：** 在现有 Pi 插件市场可以找到该沙箱插件，用户能看到真实的
  安装/启用结果；运行时能留下可关联的验证、TraceStore 和 EvalRun 收据，未
  取得相应收据的边界继续标为未验证。
- **原话依据：** “沙箱一个pi有插件市场是有的。”来源：当前任务，线程
  `codex://threads/<redacted-current-thread>`，2026-08-28。

### UR-193 — 交付前整理全部相关文件，并在本地提交后合并到 main

- **状态 / 优先级：** `current / P0 delivery and archive`
- **真实需求：** 当前工作结束前，先把与本次 PAWOS/Room/Trace/沙箱交付有关的
  源码、测试、技能、需求文档、状态和 handoff 全部整理清楚，清理已替代或过时
  的重复路径；随后创建真实本地提交并把交付结果合并到 `main`，留下可继续开发
  的归档基线。
- **必须保留：** 不相关的用户改动、真实数据、隐私文件和明确排除的 Browser/
  Ego 路径不得被覆盖或带入提交；归档基线必须能从实际 Git 提交和检查结果恢复。
- **禁止：** 不得只根据“完成”文字、截图、暂存 canary 或旧 handoff 声称已
  提交/合并；不得为了形式增加无关的 hash 门槛，也不得在未审计路径前整树提交。
- **用户可见验收：** 交接时能给出最终提交、`main` 合并结果、归档位置、整理
  范围、真实检查与仍未验证的安装/前台边界；后续开发默认从该基线继续。
- **原话依据：** “结束后合并到mian，然后我交给一个前端模型检查和优化，看看是否完成最近需求，然后好好的归档了，我们这个项目，后续我在归档基础上开发。”来源：当前任务，线程
  `codex://threads/<redacted-current-thread>`，2026-08-28。

### UR-194 — 外部前端模型在归档基线之后接手复核和优化

- **状态 / 优先级：** `current / P0 external handoff`
- **真实需求：** 本地整理、检查、提交和 `main` 合并完成后，再把完整且可发现的
  文件与文档交给另一个前端模型；该模型负责对照最近需求检查是否完成并继续做
  前端优化。交接入口必须能发现需求总索引、逐字证据、状态、Cloud Model、相关
  handoff 及真实检查边界。
- **必须保留：** 外部模型接手的是归档后的当前基线，不是旧版前端、孤立截图或
  部分文件；当前需求的原话、修正关系、未完成项和验证空白都要可追溯。
- **禁止：** 不得在文件未整理、提交未完成或 `main` 未合并前把交接称为完成，
  也不得让外部模型依赖本机 ignored `/docs/`、私有历史或不可复现的运行状态。
- **用户可见验收：** 另一个模型从 [CLOUD_MODEL.md](../../../CLOUD_MODEL.md)
  进入即可定位当前 `main` 基线和最近 UR，不需要扫描整个仓库猜测哪些文件是
  当前入口；它能明确区分已检查、未检查、已安装和未证明的边界。
- **原话依据：** “你要全部文件整理好，在提交，我再给另一个模型。”来源：当前
  任务，线程 `codex://threads/<redacted-current-thread>`，2026-08-28。
