## User Requirement Ledger

### UR-215 — 单角色、未分配和最终结果不能套用 Room 表格

- **状态 / 优先级：** `current / P0 Room information architecture`
- **当前控制要求：** Room 只有一个实际角色/行星时，不显示多角色任务表；没有分配
  角色的单行星起始态继续显示 Grill Me 等起始动作；回合结束后的结果行星单独展示
  结果，不塞回任务表。只有多个真实已分配协作角色时才使用表格。
- **必须保留：** 单角色身份、当前任务、状态、公开进展和结果仍可见，只改变布局。
- **不得：** 用空列、巨大空白或一行伪表格冒充多角色协作。
- **验收：** 1 个角色为独立卡/面，2 个及以上已分配角色才出现表头和多行表格；结果
  分面不显示协作任务表。最终结果由明确负责人单独汇报并在表格外可见，用户无需展开
  某一行才能发现本轮结论；结果面仍可回到该负责人的 Session 与完整过程。
- **来源原话：**

  > 那个，行星是表格对吧。两种情况不能表格，就是单行星没分配的时候，这时候有grill me这些。第二，结束后提交结果，那个结果行星不能表格，得单独

  > Room模式里面只有一个回答的时候，就只安排了一个角色的时候，就不要显示表格。

### UR-216 — 一条用户消息只能投影一次

- **状态 / 优先级：** `current / P0 conversation correctness`
- **当前控制要求：** 一次发送只产生一个用户可见消息。Session transcript、Room Root、
  participant mirror、恢复快照和增量事件可以有多个内部来源，但 UI 必须按稳定因果身份
  去重，不能显示成多条相同消息。
- **不得：** 依赖文字相同做模糊去重，或删除真实不同轮次；必须使用 message/turn/root/
  dispatch 等权威身份。
- **验收：** 初次发送、流式更新、断线重连和刷新恢复后，仍只有一条用户消息。
- **来源原话：**

  > 然后目前有非常多的情况下，就是发送一条消息，它显示很多个。

### UR-217 — 长 Tool/思考活动必须可折叠且默认紧凑

- **状态 / 优先级：** `current / P0 conversation operability`
- **当前控制要求：** Tool、思考过程和重复进度默认显示紧凑摘要；整组以及单项均有明确
  的展开/收起控制，用户收起后不会被新事件强制重新展开。
- **必须保留：** 失败、待审批、当前正在执行和终态仍可被看见；折叠不删除证据。
- **验收：** 长工具序列不会把 Composer 推出可操作区域，键盘和鼠标都能展开/收起。
- **来源原话：**

  > 还有就是发一个消息，然后它那个工具列表我没办法折叠，导致非常非常长的工具。

### UR-218 — Composer 在运行、滚动和恢复期间始终可见可操作

- **状态 / 优先级：** `current / P0 composer reliability`
- **当前控制要求：** 输入框不能因流式事件、自动滚动、Room/Session 状态切换、resize、
  恢复或错误投影而消失。运行中仍可输入 Steer；终态后可立即发下一条。
- **验收：** Composer 始终有稳定布局槽位与焦点路径；出现错误或加载慢时也不能卸载。
- **来源原话：**

  > 还有就是显示bug，就前端会那个输输入框突然会消失，这个就没办法输入和操作了。

### UR-219 — 对话打开性能必须先定位数据库、传输和渲染边界

- **状态 / 优先级：** `current / P0 performance and architecture`
- **当前控制要求：** 对话打开和输入响应不能长时间无反馈。修复前必须分别测量 SQLite
  查询、HTTP/SSE/快照传输、前端归并与 React 渲染，不凭感觉重写连接方式。
- **必须保留：** 历史、Tool 证据和恢复能力；性能修复不能通过静默丢数据实现。
- **验收：** 形成可重复计时基线和分段证据；确认瓶颈 owner 后再做最小修复，并用相同
  Session/Room 数据复测。若需要改连接方式，必须有对照证据证明不是数据库或渲染问题。
- **最新可见性能目标：** 用户消息与路由/admission 回执应立即出现；消息正文优先于 Tool
  详情，Tool/思考细节可以稍晚补齐。对用户指定的同一冻结 Room/Provider Case，冷路径从
  点击发送到首段可见 Provider 正文目标为 **3–7 秒**。若 Provider 服务不可用必须即时显示
  真实失败；不能用预生成文本冒充首段回复，也不能把 70 秒归因给“模型冷启动”而缺少分段证据。
- **多窗口一致性：** 主 Room、行星与卫星窗口必须先快速显示同一真实 transcript 的完整
  message skeleton，再实时合并正文、Tool 和终态；不得以速度为由换成摘要、截断历史或各自
  拉取不可对账的副本。

### UR-220 — 安装快照必须包含当前已接受的前端要求

- **状态 / 优先级：** `current / P0 installation integrity`
- **当前控制要求：** 不能从旧基线只摘取最后一个功能后就称为“最新版安装”。安装前要
  核对当前接受需求、对应 owner 文件和候选快照的差异；任何未进入候选的已接受修复必须
  明确阻塞安装或被列为未包含，不能静默丢失。
- **验收：** 安装候选对 UR-215–UR-219 以及同批前端 owner 有明确清单、测试与真实前台
  验收；installed marker 与该候选绑定，旧版本保留回滚点。
- **来源原话：**

  > 为什么你安装的很多和我之前要求的不一样

  > 你之前说了的，为什么你而且也做了，为什么安装不一样？
