| PagerDuty SRE Agent：交互式调查 | 工程记录描述用户中途补充假设、持续进度、取消和恢复；最终将同一次调查的子任务放在同一进程，由持久化的主管保存恢复状态。 | 运行页要支持补充线索、停止和恢复；进度来自执行事件。[工程原文](https://www.pagerduty.com/eng/inside-pagerdutys-sre-agent-how-we-built-deep-incident-investigation/) |

| GitHub Copilot：代码审查 | 用已知代码问题做内部测试，再看真实 PR 中的反馈及问题是否在合并前修复；结合仓库与关联 Issue 解释审查意见。 | 展示 diff、具体问题、修复证据和误报；评论数量不代表质量。[产品工程记录](https://github.blog/ai-and-ml/github-copilot/60-million-copilot-code-reviews-and-counting/) |
| Anthropic Research：多 Agent 调研 | 用真实使用模式的问题迭代，结合来源、引用和完整性评分与人工检查；生产追踪用于定位工具与查询失败，版本切换保留运行中的旧任务。 | 展示来源链、调查覆盖、恢复记录；不同有效调查路径不必完全一致。[工程原文](https://www.anthropic.com/engineering/multi-agent-research-system) |

这些案例支持共用实验管理，但不支持把全部业务改写成资料问答。下文是据此提出的 PAW 设计，不是上述团队 UI 的复刻。

## 云上诊断：先还原两个相互连接的过程

一次事故处理：告警与影响范围 → 查询证据 → 验证根因 → 执行处置 → 观察恢复 → 复盘。

改进诊断 Agent：挑选已知事故 → 保存可重放环境与标准 → 运行现有版本 → 定位失败 → 修改一个因素 → 对照验证 → 应用版本 → 从新事故继续收集证据。

Lab 主要承接第二个过程，并链接第一个过程留下的事实。诊断正确、处置成功、服务恢复是三个不同结果。

| 步骤 | 用户需要完成什么 | 必须留下的结果 | 页面重点 |
| --- | --- | --- | --- |
| 1. 选事故 | 确认事故来源、影响对象、观察时间和症状 | 原事故引用；快照或可访问环境 | 事故摘要、服务与时间；一个继续入口 |
| 2. 核对环境与标准 | 检查允许查询的数据、已知根因和验收方法 | 可重放输入；与 Agent 可见资料分开的参考答案 | 数据缺口、环境可用性、标准来源 |
| 3. 跑现有版本 | 用当前配置重做诊断 | 真实工具调用、证据摘要、排序后的根因、失败与用量回执 | 调查时间线；可展开原始证据 |
| 4. 定位并修改 | 判断是缺数据、选错对象、误读日志、工具失败还是规则问题 | 改动原因、版本差异、保持不变的条件 | 一项变更及它针对的失败 |
| 5. 对照验证 | 同一输入运行候选，检查不同故障分组和未参与调整的案例 | 逐案前后结果、退步项、未知项、成本口径 | 联合根因结果在前；成本与耗时在后 |
| 6. 应用与反馈 | 指定版本生效位置，核查新运行，保留可恢复的旧版本 | 应用回执、后续运行与回退依据 | 生效范围、当前版本、下一步 |

业务正常处置的审批、权限与发布流程由原系统拥有。Lab 不凭一份评分报告推断线上处置已经执行。

## PAW 本次核实到什么

- 数据来自 [Cloud-OpsBench](https://github.com/LLM4Ops/Cloud-OpsBench)，属于 Kubernetes 故障快照基准。公开项目提供告警、资源、日志及部分案例的指标，通过缓存工具重放。不能称作 PAW 的客户生产事故。
- 本地 `cloudops-smoke-v1` 含 12 案、两个系统、3 × 4 批次。源版本为 `49120feff966e2903f85cf60805b4ca9a0f95027`；本次用 `CloudOpsBlindSuite` 成功读取，题集和诊断合同身份与已保存运行一致。
- 本地参考根因与评分脚本存在。当前常驻服务的实际场景登记仅返回 `memory`；CloudOps 数据存在与前端可启动是不同状态，尚需应用层登记环境。
- 现有运行使用真实 Pi Session 和只读 `cloudops_benchmark` 工具：读取索引、查询观测、提交诊断。它没有执行修复集群或验证线上恢复。
- 评分器对首位 `fault_object` 与标准比较得到 CA，对首位 `root_cause` 比较得到 FA，两者同时命中得到 JRA。Top-3 JRA 看前三项中是否有联合命中；AnswerCoverage 单独计算。旧 UI 中 CA、FA、JRA 的若干中文名称与此不符，本轮修正显示名称，保留原始分数。
- 现有 r5 记录的组件命中为 12/12，联合根因为 11/12。末个 performance 案例的 FA、JRA 未通过。因此“组件全对”不能展示成“全部根因诊断正确”。[逐案记录](../../../eval/interview-metrics/runs/cloudops-luna-max-owner-mechanism-prompt-case-projection-20260904.r5.json)
- 本地安装中的资料问答流程仅执行 `context_qa` 和 Prompt 对照。四题流程验收不会成为 CloudOps 生产效果证据。

## 展示与交互规则

1. 先说明正在解决哪起问题，再显示配置。每步都说明输入、当前结果和下一步；缺少环境时给出具体缺项。
2. 标题、主要结论、证据、技术细节分层。大标题约 24–28px，步骤标题 18–20px，正文 14–16px；窄窗口按内容重排。
3. 云上诊断先呈现 JRA 的逐案比较；CA、FA 与工具失败用于解释差异。成本、延迟和调用量具有独立口径。
4. 同类前后指标使用相同尺度，并同时显示分子和分母。以颜色、文字和图标共同标识改善、退步、未知；未知值不画成零。
5. 点击失败案例能回到输入、工具结果和判断依据。基线与候选并排显示；窄窗口上下排列且保留明确标题。
6. 时间线区分事故发生、Agent 调查、版本应用；缺失时间不补造。动画只表达真实状态变化，运行中不推测百分比。
7. 先突出失败机制、修复决策、验证结果和边界，再按需展开哈希、Session ID 和原始日志。

## 早期实现建议与当前适用范围

以下是本次需求澄清前的实现建议，保留作为路径资料。继续实施时先按
UR-289、UR-290 核实环境、合理简单基线与优化空间，再决定首个候选实验；
连通一个只读调查流程不等于已完成 UR-284 的成功率/成本优化。

1. 先修正已确认的指标文案、流程恢复和资料问答适用范围。
2. 为 CloudOps 连接本机已核实的快照、评分器与 Pi 环境，复用现有场景登记和任务回执；通过前端启动并检查一条完整调查。
3. 将事故摘要、观测证据、逐案对照和版本范围整合到现有 Lab，保留原运行与失败记录。
4. 以同样的输入、执行、验收、应用接口接入其他真实业务。每个场景分别提供任务数据与判定器；不得因增加名称和配色就标记为已支持。
5. 生产连接、处置动作及恢复验证只有在对应系统和证据接入后，才显示为可执行或已完成。
