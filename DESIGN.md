# PAWOS interface direction

Accepted direction, 2026-09-05. Implementation status is tracked separately in
OUTCOMES.md and the PAWOS requirement ledger; this file is a design contract.

PAW is a working environment for conversations, collaboration and experiments.
It uses opaque reading surfaces, quiet structure and a coherent stellar
identity in selectable light, dark and system themes. The user explicitly
authorizes replacing all previous layouts. The
old five-panel Room and oversized Home chooser are rejected references.

## Reading and action

- One principal task and one obvious next action per surface. Start with the
  user's goal, the current result and the action needed to continue.
- Keep main conversation text around 640–800px when space allows. Preserve a
  usable reading column before opening secondary information.
- In collaboration mode, every partner participating in the current execution
  has its own visible window. Selecting another planet focuses its window
  without hiding previously opened partners. New execution participants open
  incrementally; completed windows retain their results. Unassigned idle
  partners must not manufacture activity or duplicate the moderator's result.
- Show provenance, tools, settings and diagnostics at the point they help a
  decision. Avoid parallel navigation that repeats the App sidebar.
- Make empty states specific to their filter/date. An empty day is not an empty
  memory library. Offer a real next action without manufacturing activity.

## Shared controls

Home and live conversation share the ModelPicker. Reasoning is immediately
available; searchable models expand inside that same bounded popover. Selection
names remain accessible even in compact toolbars. Portals stay inside the
viewport; keyboard focus returns to the opener.

Use compact typography, 6–12px internal control gaps and 24–36px between major
sections. Primary controls remain legible in a resized App window. Minimize
bordered containers, status pills and explanatory copy. Do not use colored
cards to stand in for an information hierarchy.

## Stellar identity and motion

Small orbits and planet identity belong to navigation and idle margins. Long
text, tables and code stay on opaque, theme-aware App reading surfaces. Satellite
counts come from actual child Sessions and distinguish unavailable data from
zero.

The built Stellar desktop is a cinematic blue/violet luminous nebula scene with
a ringed planet at the right edge and bounded near-star particles. Multiple
confirmed running Sessions have distinct planetary identities; decorative
worlds and orbital geometry never assert execution or collaboration. Layered
depth keeps launcher labels legible. The latest requirement adds a dark
universe alongside light mode. No catalog seed was chosen; seed is N/A because
this is a user-directed extension of the existing OS.

The system mark is a static ringed world and guiding star, replacing the paw
print in system chrome and icon assets. Live thinking uses measured spiral
rotation; Tool execution uses orbiting satellites. Waiting and terminal states
remain still. This movement belongs to the execution indicator, never the
reading text or the brand mark, and stops offscreen or under reduced motion.

Project folders open directly into a full-viewport, code-rendered galaxy
painting. For this surface, the user's later direction is beauty first:
“首先是美，实用性不怎么要求” and “任你发挥，美就行”. The source now uses
an asymmetric oblique spiral, deep blue ink, cobalt/cyan pigment ribbons,
selective ivory/gold ridges and a warm center. Following “质感不对，粒子太少，不过柔和酷炫”,
the wash and curved strokes recede beneath dense fine stardust and a sparse,
deeper luminous layer. Keep the soft flow while making grains visible. Real tasks
appear as small lights; labels emerge on approach, selection or keyboard focus.
The earlier flat image grid, spherical-world composition, holographic targets
and repeated particle pinwheels are superseded for this project surface.

Project identity and serif headings sit at the upper left; docs/list actions
and pause/speed controls stay peripheral. Selection reveals actual public
progress, child model identity and project documents, without a redundant
detail eyebrow. Room counts may show completion; ordinary Sessions never
receive an invented percentage. The painted flow is ambient artwork, not a
claim of execution. Preserve keyboard access, returned focus, narrow layouts,
unbound-workspace recovery, hidden-window suspension, reduced motion, lazy GPU
loading and disposal. The desktop wallpaper and Browser are separate surfaces.

This is a source implementation description, not installation or user visual
acceptance. No approved comp exists and no raster is used by this renderer;
the abandoned generated reference is review history only. The direction was
user-pinned with no Impeccable concept roll; the project hash varies pigment,
not the design choice. Composition and source references live in the scoped
project-galaxy surface brief under `.impeccable/surfaces/`.
The thought indicator's core and orbit must remain geometrically concentric,
even inside a status strip that lays its text spans out differently.

Pointer response uses three spring parallax planes at 6/20/34px (far nebula,
planet and near stars). The scene pauses whenever an App or window interaction
owns attention, while the document is hidden, during drag/resize, under
reduced-motion preferences, and for coarse or non-hover pointers; the static
sky remains. The latest user rejection, “星际要酷炫，当前这个不行”, is the
quality bar for future Stellar refinement.

Motion communicates a change: active tool work, a disclosure, or selection.
Terminal events stop activity feedback. Streaming does not repeatedly animate
old text or collapse a user's expanded evidence. Respect reduced motion, stop
ambient work in hidden windows, and retain the user's reading position.

The final Stellar captures and independent review cover this four-finding
correction only; they do not establish whole-OS, native-host or
motion-performance acceptance.

## Truthful recovery

Pi owns execution and terminal state. An active Room record or incomplete task
list is not proof of a running turn. A failed send retains its draft and names
the actionable condition. Synchronization and resubmission are different
operations; an uncertain request must be reconciled before another effect.

## Completion criteria

Each App needs its actual main flow, loading, empty, failed, recovery and narrow
window states checked. A shared theme or a successful build does not establish
whole-system acceptance. Source, installed product and live execution evidence
are reported separately.
